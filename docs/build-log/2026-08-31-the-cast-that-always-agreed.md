# The cast that always agreed

The check itself was one line, and it looked unambiguous: a certificate's Key Usage
extension had to be exactly `digitalSignature`, nothing else. Not `digitalSignature` plus
`keyEncipherment` — that's the *other* certificate profile, the one this code exists to
tell apart from this one. Get that wrong and the whole reason for having two separate
certificates (so a stolen telemetry-signing key can never be waved around as proof of TLS
identity, or the other way around) quietly stops holding.

The library's Key Usage type wasn't a plain integer. It was a flag set — a small wrapper
around a bitfield, with named constants for each bit. To compare it against "exactly
`digitalSignature`," the natural-looking move was to pull the numeric value out of both
sides and compare those: `key_usage.bits() != KeyUsages::DigitalSignature as u16`. It
read fine. It compiled without a warning. It matched every intuition about how casting an
enum to a number is supposed to work.

It also always evaluated the right-hand side to zero.

The flag-set type wasn't a C-style enum with `DigitalSignature = 1`, `KeyEncipherment = 2`,
and so on, the way `as u16` assumes. It was generated by a macro into something with its
own internal shape, and casting one of its variants straight to an integer didn't reach
the bit value at all — it reached whatever the macro's own representation happened to put
there, which was not the number anyone had in mind. The check was still running. It just
wasn't checking anything real: `bits() != 0` is true for almost every certificate that
will ever exist, so the comparison "worked" by accident, on every certificate that should
have passed *and* almost every one that shouldn't have.

It surfaced because the honest test — feed it the certificate that's actually supposed to
pass — refused to pass. Not a subtle failure buried in a log; the whole certificate was
rejected outright, with a message insisting its Key Usage was wrong when it demonstrably
wasn't. That's the version of this bug worth being grateful for: the one that breaks
loudly on the case you're watching, not the one that quietly waves through the case
you're not.

The fix was smaller than the bug: the flag-set type already knew how to compare itself to
one of its own named variants directly, no casting required. Swap the cast for that, and
the same line goes back to meaning what it always looked like it meant.

What made this worth a second look wasn't the one line — it was the reason to go looking
for its siblings. A fresh-context, differently-built reviewer was asked to assume the
author was overconfident and find what a same-day, same-author re-read wouldn't catch. It
found four more, in the same neighborhood: a private-key-matches-certificate check that
compared raw bytes but never confirmed those bytes claimed to be the algorithm they were
being compared as; every test certificate in the directory carrying a "this is a
certificate authority" flag that nothing was checking for, left over from generation
commands that never set it explicitly; a `key_ref` that a caller could, in principle,
supply independent of the key that actually signed anything, when the entire point of the
surrounding type was that the two could never disagree; and a fixture's own comment
promising a regeneration recipe that would, if anyone actually ran it, produce a
different, equally valid, but non-matching signature.

None of the five were the kind of thing a clean build or a green test suite would have
caught on their own — each one had a passing test sitting right next to it, testing
something true, just not the thing that mattered. That's the pattern worth remembering
past this one session: a check that compiles and a check that's correct are not the same
claim, and the gap between them is exactly where a second, colder read earns its keep.

Full findings and fixes are in `docs/decisions.md`'s 2026-08-31 entry.
